## Agency reuse and ownership

### Library

Start with the selected project's authenticated file and path routes, the thread storage file tree, and the file preview tab. The project routes support a selected environment, and the preview shell already resolves project, host, workspace, and thread files. Source links can use the existing project and thread navigation. [Project routes](../apps/server/src/routes/projects.ts) · [Thread storage tab](../apps/app/src/components/right-panel/tabs/thread-storage.tsx) · [File preview shell](../apps/app/src/components/right-panel/shell/file-preview-tabs.tsx)

A project-wide Library needs an index for deliberately published agent outputs. Record the project, storage location, relative path, original thread ID, and media type at registration. A file discovered in the project tree can appear as a project file without claiming a source thread. Permission checks apply separately when resolving a preview or opening the producing thread. Reuse existing file preview rendering for documents and media and provide an authenticated download when a format has no viewer. Cover and download handling must resolve the current project on the server.

### Preview, live hosting, and the Admin tab

Agency's Browser already renders arbitrary user navigation. The Core's `room-cli preview` registers an agent development server and exposes a private local URL through its paired helper. Browser tab state carries a URL, thread and environment context. The preview registry tracks ports for a paired Core. A published site record is the missing association that tells the panel which app is selected. [Core preview docs](../../core/docs/previews.md) · [Browser tab](../apps/app/src/components/right-panel/tabs/browser-tab.tsx) · [Browser tab model](../apps/app/src/components/right-panel/store/tab-model.ts)

- [#45](https://github.com/getwinharris/agency/issues/45) owns the project preview URL, publish and rollback operations, subdomain reservation, domain verification, runtime lifecycle, and TLS. Validate the ready preview independently of deployment health. Run the published release under a hosting lifecycle that survives closing the creating thread. Keep platform cookies, CLI credentials, and other projects' secrets outside hosted app requests.
- [#53](https://github.com/getwinharris/agency/issues/53) owns the project-scoped Hosted Sites inventory, selection, deployment activity, and per-site traffic analytics. Show traffic for the authorized selected site, with its production origin, deployment status, and time range.
- [#54](https://github.com/getwinharris/agency/issues/54) owns the optional app starter and the app's `/admin` route. App owners and staff sign in to the app. App authorization governs the forms inbox and account activity independently of [Team #47](https://github.com/getwinharris/agency/issues/47).

Use the existing right-panel shell to show Admin beside Browser when the selected site's server-authorized record confirms its project, verified preview or production origin, and app Admin opt-in. Resolve the fixed `/admin` path on that origin and open it with the Browser's normal isolated session. The current Browser address is navigation state. The selected site record supplies the association, and the app authorizes users at `/admin` and on each protected operation. A site change must rebind the panel and prevent a previous site's Admin session or tab from appearing in another project. [Existing thread panel](../apps/app/src/views/thread-detail/ThreadDetailView.tsx)

### GitHub skills and plugin discovery

Agency already has a Tools Skills library backed by a skills.sh registry with a GitHub source for each entry. The Agency plugin marketplace separately accepts validated HTTPS manifests and `git:<url>@<ref>` sources. `getwinharris/skills` is a GitHub source for `SKILL.md` directories and documents native readers including Codex, Claude Code and Pi. Its README lists skills by name and description with shared installation guidance. [Skills library](../apps/app/src/components/tools/SkillsLibrary.tsx) · [Registry adapter](../apps/app/src/lib/skills-registry.ts) · [Marketplace source handling](../apps/server/src/services/plugin-catalog/marketplace-source.ts) · [GitHub skills source](https://github.com/getwinharris/skills)

Use the centralized GitHub catalog for the discovery view. Identify each item by canonical repository and item path, or by repository and marketplace plugin ID when the manifest defines one. Each item needs its source, declared or verified CLI compatibility, prerequisites, and native installation instructions for each supported CLI. Show unknown compatibility as unknown. Keep Agent Skills and MCP portable. Agency UI plugins run through the existing Agency plugin runtime. The selected agent's workflow performs native installation. ## Sample app acceptance

Record the tested commit, project identity, app URL, runtime revision, and pass or pending result for each check. Use disposable accounts and project data.

| Check | Evidence to capture |
| --- | --- |
| Publish and reopen | Open the sample at its assigned HTTPS hostname, record the release, close the creating agent session, and reopen the live app. Check a custom domain and certificate when a test domain is configured. |
| Two verified sign-ups | Complete the email verification flow with a disposable address and the Google flow with a separate disposable account. Sign in again. Admin must report one verified signup by each original method and separate sign-in activity. |
| Lead intake and assignment | Submit a public form. As the app owner, open Admin beside Browser. Confirm that the form is in the inventory and that the submitted enquiry can be searched, assigned, given status and notes, and exported. Follow the lead link back to that exact submission. |
| App and platform isolation | As staff or customer on app A, attempt to open the corresponding protected routes on app B and the bapX workspace. Check app A's staff and customer permissions independently, and verify that platform cookies are absent from both app origins. |
| Preserve records | Submit on the first schema, change the form, deploy the new release, submit again, and roll back the release. Reopen both submissions and both user records. Historical submissions should retain their original field identifiers and data. Check that project data stays outside both the served root and the release directories. |
| Confirm opt-in | Publish a separate app without the starter when the hosting lifecycle is available. The sample app's account, form data, and Admin tab must stay scoped to the sample. |

Live publication, domain binding, and the selected-site Admin tab depend on #45 and #53. Real email verification and Google sign-up require configured test providers for the sample app. A local preview and provider fixtures can verify app behavior and persistence while those live checks remain open.
